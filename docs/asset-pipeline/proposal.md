# Asset Studio: structure and publication proposal

**Status: approved and implemented for the image workflow and runtime migration.** See the [Studio guide](studio.md) for current behavior, commands, validation and remaining model-provider work. The following is the reviewed design; aspirational details beyond the first version remain explicitly scoped in that guide.

Read this first, then the [audit findings](audit.md) and [generation pipeline](pipeline.md).

## The decision

Build **Asset Studio** inside the existing `tooling/` Vite app. Give every asset a stable identity, an editable source record, a validated game export, and a visible history. The folder tree should be understandable without the app; the app should make it unnecessary to remember paths.

The most important rule: **a provider response is a candidate. It becomes a game asset only after validation and approval of its final, game-sized appearance.** This applies equally to OpenAI images, Meshy models, purchased packs, manual Blender work, and assets generated by an agent.

There is already useful infrastructure: a separate Vite entry point, a content validator, a Blender studio, character exporters, and vegetation validation. Reuse their capabilities behind one publication service. Do not maintain separate rules for a person clicking Save and an agent copying files.

### Why separate source and runtime?

An icon has a 1024px authoring image and a 128px game image. They are the same logical asset with different jobs. A Blender document can generate many unit variants or all 38 vegetation meshes. A HUD rim has an image plus opening geometry. Modeling those relationships explicitly is cleaner than putting every working file beside every shipped file.

Source records should allow either a local `source.blend` or a reference to a shared source and export object/collection. Do not create three divergent ant-family Blender copies, or copy the entire purchased pack into every tree folder. Meshy imports retain the provider's original export and a Blender working document once imported; that document is not misrepresented as a hand-authored procedural source.

Approved masters, reference inputs and provenance belong in backed-up versioned storage. Start with the repository and use Git LFS for large binaries once configured and verified on the hosting service. `.asset-work/` is disposable working history, so publication must first promote everything needed to reproduce the accepted derivative into `art/`. A seed or prompt cannot guarantee regeneration of an identical AI image; retaining its actual bytes can.

## Naming and identity

- New path segments: lowercase ASCII kebab-case. No spaces, `final-final`, timestamps, model-provider names, or `v1/v2` directories in published filenames.
- Icons stay flat as requested. Prefixes disambiguate purpose: `command-`, `unit-ants-`, `building-ants-`, `item-`, `resource-`, `stat-`, `ability-ants-`, `research-ants-`.
- A model's folder gives its identity; its primary export is always `model.glb`. Supporting filenames describe their role, such as `collision.glb`, `lod-1.glb`, or `normal.png`, only when required.
- Display names are editable: **Worker**, **Mound**, **Heart of the Forest**. They do not determine identity after creation.
- Existing content and scenery IDs remain stable, including `icon.ants.settler`, `asset.ants.fort`, and `tree_primary`. A filename can become `tree-primary/model.glb` without renaming the map's `tree_primary` reference. Do not guess mappings from display names.
- New IDs are namespaced, such as `icon.item.heart-of-the-forest`. Naming conflicts fail visibly. “Replace existing asset” must be an explicit operation, never an automatic numeric suffix that silently creates the wrong asset.

Revision numbers and hashes belong in metadata and history. Runtime references continue to resolve a stable ID. Cache invalidation uses the published content hash; URLs for different revisions must not reuse stale browser data.

## One asset record, one runtime manifest

Each `art/.../asset.json` owns:

1. ID, display name, kind, faction where relevant, tags and lifecycle state.
2. Source location or shared-source reference, exact source hash, origin and retained references.
3. Output profile and transform recipe: target path, dimensions, crop/fit, color handling, alpha requirements, or model export settings.
4. Provider job/provenance link, when generated; manual imports are first-class too.
5. Approved revision, validation report and approval of the final derivative.
6. Dependencies: shared textures, model LODs, animation profile, source pack. No inference from neighboring files.

The publisher compiles **one runtime manifest**, containing only approved exports and render metadata. Game definitions refer to IDs; they no longer duplicate disk paths. The editor derives its model library from that manifest. Retire the parallel `content.assets` file listing and `catalog-archive.json` fallback at cutover, after their needed entries have been explicitly classified and migrated. An archived asset can remain discoverable in Studio without being automatically available to the game.

Some existing resources have both a render ID and a scenery binding: `asset.resource.tree-primary` binds to map asset `tree_primary`. Keep that binding in the same record and validate both lookup indexes. Multiple logical variants may deliberately share one exported file; declare the relationship instead of copying the mesh or maintaining two editable path listings.

Keep ownership of data clear:

- Asset record: model, icon, render scale, portrait framing, material/animation profile, decorative light/deck geometry.
- Entity definition: HP, damage, speed, costs, collision/placement rules that affect gameplay.
- Scene placement: asset/definition ID, position, rotation, scale, owner and authored instance state.
- Map editor: consumes the same scenery metadata for bridge decks/blockers that the game uses; migration must not change their values.

The current content fingerprint includes assets and their paths. A folder migration therefore changes compatibility checks even when artwork is byte-identical. The migration must either explicitly version that content revision and its save policy, or split gameplay and art fingerprints with dedicated save/network tests. It must **not** bypass an existing mismatch check and assume old saves are safe.

## The Studio experience

Use `npm run dev:tools`. The app is already separate from the game. Its current default port, 5174, also appears in the docs workflow; choose a free dedicated Studio default (for example 5175) rather than starting conflicting servers.

### Library

A searchable, paginated library with filters for Icons, Interface, Models, Textures, Audio and Maps; faction and tags are secondary filters. Start with icons fully editable and the other categories inspectable. Show filename, ID, actual dimensions or geometry metrics, source, current revision, validation and “Used by”. Keep unused approved assets, drafts and archived assets visibly distinct.

Choose reference art from **approved style collections**, not every PNG under `icons/`. Current icon generations differ in quality and age. Automatically suggest a small, relevant set, show the thumbnails, and let the user replace them before submission. Folder-based classification bootstraps migration; metadata becomes authoritative afterward.

Use a virtualized or paginated grid and small cached thumbnails. Do not preload 167,000 sprite files or instantiate hundreds of GLBs to open the library. Inspect a selected model on demand, with the same lighting/material conventions used by the game.

### Create an icon

1. Choose **New → Icon**, type “Heart of the Forest”, and select Item.
2. Studio proposes `icon.item.heart-of-the-forest` and `assets/icons/item-heart-of-the-forest.png`.
3. Pick the painted item style. Studio suggests three approved item icons, preferably their retained masters. Show their exact identities and revisions. Existing 128px art is usable when that is all we have; mark it as a runtime reference rather than inventing a higher-resolution source.
4. Write the subject; adjust reference selection and API controls. Preview the assembled prompt and cost estimate before generating.
5. Generate candidates into the job workspace. Inspect the full image and **128px/64px previews in a real command/inventory slot**, including adjacent existing icons.
6. Choose one, adjust framing if needed, inspect the final derivative, then **Publish to library**. Studio writes the canonical files and manifest, and reports the resulting path.
7. Optionally use **Assign to…** to link an existing item/action definition. Publishing an image does not invent item stats or silently replace a gameplay icon.

There are separate operations for generating a new image, making a variation, and replacing an existing asset. Replacement retains the ID, shows affected consumers, and advances its revision.

### Interface assets

These use the same job/publication system with different profiles. A transparent rim is not an icon with a wider aspect ratio. It has a declared opening, protected empty regions, border thickness, sizing behavior and a separate programmatic background. HP/MP fills have their own textures and left-to-right clipping contract. See [pipeline profiles](pipeline.md#output-profiles).

## Technical shape

Use the existing Vite/TypeScript UI and a small **local Node authoring service**. No database is necessary initially: JSON metadata and job records are sufficient, with a rebuilt search index. Native desktop packaging can reuse the existing Tauri shell later.

```text
Studio UI or agent CLI
        ↓ same typed operations
Asset service: Library · Jobs · Validation · Publication
        ↓                     ↓
Provider adapters          local image/model processors
        ↓                     ↓
Retained sources and candidates
        ↓ explicit final approval
Canonical runtime manifest + approved files
        ↓
Game, editor, wiki
```

Use a pinned image-processing library such as Sharp for deterministic image decoding/resizing/encoding, plus existing Blender exporters for models. That is a proposed dependency; it has not been installed. The server owns filesystem access, provider credentials and jobs. The browser owns the editing workflow and previews. Keep all of this outside simulation and lockstep.

The service exposes the same operations to the UI and a future agent CLI/MCP adapter: list/search, inspect, create job, submit, observe, validate, publish, assign, replace and archive. Do not make browser clicks the only supported production workflow. Also do not allow agents to bypass publish validation by writing arbitrary output paths.

## Future 3D generation

Reserve the provider boundary now; implement it later:

**Existing model or images → approved concept image → Meshy job → retained mesh/textures → Blender normalization/cleanup → game validation → approval → publication.**

A model reference is rendered into consistent views for an image-based concept request; do not pretend an image API understands raw GLB bytes. The concept stage and 3D stage have separate approvals and costs. Regenerating the concept invalidates any pending “approved reference” relationship.

Meshy's API provides asynchronous image-to-3D jobs, progress, textured model downloads including GLB, and geometry controls. Its target polygon count is approximate. Download successful outputs promptly and retain the original result; provider download URLs can expire. A successful generation does not establish our scale, material, animation, or performance contract. [Meshy image-to-3D reference](https://docs.meshy.ai/en/api/image-to-3d)

Do not promise automatically game-ready animated ants. Start that phase with static environment/building assets. Skinned units must additionally satisfy the existing animation, socket, team-color and combat-contact contracts. Keep our Blender path available for correcting and animating generated meshes.

## Implementation order after review

1. **Make the structure enforceable.** Define metadata/profile schemas, build the publisher and dry-run migration plan. Import current approved sources and outputs without regeneration. Confirm existing shared sources and external inputs.
2. **Cut over once.** Rewrite runtime references together, replace broad globs with manifest-directed imports, validate all four maps, update authoring scripts/docs and remove superseded loaders. No permanent second asset system.
3. **Build the icon workflow in the existing tools app.** Library → references → generation → final preview → validation → publish/replace. Include import of manually generated files and recoverable jobs.
4. **Extend the image profiles to interface rims and fills.** Use actual alpha validation and in-HUD previews before regenerating the woodland UI.
5. **Add Meshy later.** Concept approval, asynchronous provider jobs, model inspection and Blender export. No Meshy key is needed for this audit or design review.

The first app milestone is complete when we can generate **Heart of the Forest**, publish one 128px icon with retained source/provenance, assign it to a definition, reopen Studio and see the same history, and load it in-game with no hand-copying or path edits. Repeat the same lifecycle from an agent command. A fake-transparent rim, invalid icon size, stale replacement approval or failed provider request must leave the last published asset untouched.
